# jail — передача проекта

Веб-приложение для нового обувного производства: передачи склад ↔ производство, приёмка с расхождениями, склад производства, склад готовой продукции, сдельный долг производству, статистика.

Текущая версия: **1.06** (файл `VERSION`).

## Стек и запуск
- Python + Flask + SQLite (`jail.db` рядом с кодом, создаётся автоматически через `db.init_db()`), шаблоны Jinja2.
- Локально: `pip install flask`, затем `python -c "import db; db.init_db()"` и `flask --app app run`.
- Всё приложение — в `app.py` (маршруты и логика) и `db.py` (схема, миграции, начальные данные).
- Статика: `static/app.css` (база), `static/legacy.css` (доп. стили), `static/ui.js` (общие модалки, комбобоксы, подтверждения).

## Развёртывание (PythonAnywhere)
- Аккаунт `ivnest`, адрес https://ivnest.pythonanywhere.com/jail, код в `/home/ivnest/jail`.
- WSGI-файл `/var/www/ivnest_pythonanywhere_com_wsgi.py` монтирует основное приложение (`/home/ivnest/factory`) и jail через `DispatcherMiddleware` на `/jail`.
- Переменные окружения в WSGI: `JAIL_SECRET_KEY` (значение — в WSGI-файле на сервере), `JAIL_COOKIE_PATH=/jail`, `JAIL_COOKIE_SECURE=1`, опционально `PA_API_TOKEN` (для перезагрузки через API).
- Журнал SQLite — `DELETE` (WAL на PythonAnywhere тормозит).

## Как выпускать обновления
- Каждое обновление: версия +0.01 в `VERSION`.
- Архив `jail_update_0_XX.zip` (только латиница в имени) с содержимым: `__init__.py app.py db.py VERSION static/legacy.css static/ui.js templates` (+ другие изменённые файлы).
- Пользователь ставит его сам: страница входа → «Обновление системы». Страница результата опрашивает `/version` и сама перезагружает приложение (touch WSGI + PA API).
- Статика кэшируется с `?v=VERSION`, HTML отдаётся с `no-store`.
- Одноразовые миграции/пересчёты — через таблицу `meta` и `_once(conn, key)` в `app.py`.
- Перед выпуском проверять на копии реальной базы (тестовый клиент Flask, вход через `/login/<role>`).

## Роли (вход кнопками, без пароля)
- `sklad` — Склад: Склад (переключатель «Наш» — готовая продукция / «Зона» — склад производства, только просмотр), Заявки, Приёмка, Расхождения, Справочники.
- `proizv` — Производство: Склад (остатки производства), Приёмка, Заявки, Расхождения, Справочники (только просмотр). Статистика — только у директора.
- `director` — Директор: Обзор, Склад (просмотр), Заявки (+ вкладка расхождений), Статистика, Долг, Справочники, Обновление.

## Основная логика
- **Передача на производство** = запись в `requests` (created_role='sklad'), статусы `progress → shipped («Едет») → accepted («Выполнена»)`. Позиции в `request_items`: `line_kind` = pair / material / need. Операции для пар — в `item_ops`, с **копией цены на момент добавления** (изменение цен не меняет старый долг). Заявки производства привязываются к передаче через `requests.transfer_id`.
- **Передача на склад** = `documents` с kind='RETURN' (`draft → sent → accepted`). Строки `lines`: статус gotovoe/brak, примечание, `lot` (подпись партии JSON — какие операции делались).
- **Склад производства** — журнал `stock_moves` (in при приёмке производством, out при отправке на склад, writeoff, inv, add).
- **Склад готовой продукции** — журнал `wh_moves` (in при приёмке RETURN с качеством ready/brak, writeoff, repair — брак обратно на производство через `/wh/repair`).
- **Долг** — `compute_debt`: по партиям (точные операции возвращённой партии), для старых строк — FIFO. Брак не оплачивается. Оплаты — таблица `payments`.
- Нельзя: удалить принятую передачу; принять больше, чем отправлено.
- Справочник материалов (`materials`, единицы: м2, шт, пары), названия нормализуются в Python (`_find_ref/_norm`; SQLite lower() не работает с кириллицей).
- Операции (8 шт., цены за пару): Упаковка 18, Покраска 7, Шьёт Штробель 9, Затяжка Штробель 65, Прошивка 10, Вставка обуви в колодку 15, Вклейка вставки 15, Плетение 75. Правятся директором в «Справочники → Операции».

- «Положено в передачу» и приёмка производства: сначала «Обувь», потом «Материалы».
- Приёмка: разница по строке и итог появляются, когда человек ушёл из поля (событие change), а не во время ввода (и у склада тоже).
- Заявки производства: вкладка «Обувь на склад» первая и открыта по умолчанию (название — на выбор заказчику).
- Склад производства: обувь нельзя добавить вручную, списать или пересчитать (только по передачам; сервер отвечает 403). Материалы — можно.
- Ошибки 500: понятная страница + запись в errors.log; последние ошибки видны на странице «Обновление» (свёрнуто).

## 1.05 — разбор расхождений двумя сторонами
- Таблица `discr_case` (status proposed / returned / closed, proposed_by, proposal JSON {строка: {found, left, lost}}, note, comment). Старые закрытия `discr_close` показываются как закрытые.
- Любая сторона (отправитель или получатель) расписывает недостачу по каждой строке на три итога: «Нашлось у получателя», «Не догрузили», «Потеряно»; сумма = недостача. Другая сторона — «Согласен» (итоги применяются) или «Не согласен» с комментарием (возврат на переделку). Директор только смотрит.
- Применение (`_disc_apply`): нашлось → получателю (склад→производство: recv += и приход на склад производства; производство→склад: pairs_recv += и приход на наш склад, долг растёт); не догрузили → считается неотправленным (collected / pairs_sent −=; обувь со склада производства возвращается на его остаток; брак «в ремонт» — обратно в брак склада); потеряно → остатки не меняются, не оплачивается.
- «Ошибка при подсчёте» объединена с «Нашлось у получателя».
- Цифра у «Расхождения» = разборы, которые ждут действия этой роли.
- Заявки производства: вкладка «Обувь на склад» переименована в «Отправка готовой обуви».

## 1.06
- Старые заявки, отправленные без передачи (старая схема), однократно получают строки «что едет» (`_legacy_shipped_fix`) и видны в приёмке; приёмка и расхождения больше не фильтруют по created_role.
- «Пришла часть»: `request_items.delivered` — сколько уже пришло по строке заказа. После приёмки (`_settle_request`) заказ, у которого пришло меньше заказанного, снова ждёт склад (status open, transfer_id NULL): у производства «Пришла часть», у склада «Нужно дособрать», в сборке — остаток. Кнопка «Остатка не будет» (склад или производство, `/requests/<id>/close_rest`) закрывает заказ.
- Директор может закрыть расхождение своим решением (`/discrepancies/<t>/<id>/decide`), в т.ч. спор, возвращённый на переделку. У директора появился раздел «Расхождения» (цифра — вернувшиеся споры).
- Материалы на складе склада: таблица `mat_moves`, вкладка «Наш → Материалы» (приход от поставщика, списание), расход при отправке передачи, «Не догрузили» возвращает на склад. При добавлении материала в передачу больше, чем по учёту, — предупреждение (не запрет).
- «Заявки» директора — новый вид (`_director_requests`, шаблон prod_requests.html без кнопок): «Готовая обувь с производства» / «Материалы на производство», «В работе» / «Выполненные». Старый documents.html удалён.
- Удалён старый способ приёмки по одной передаче (`/requests/<id>/recv`) и его части в acceptance.html (страница теперь только для склада).

## 1.07
- Причины списания (производство, склад) — сегменты вместо системного select.
- Производство не может добавлять материалы на свой склад вручную (stock_add → 403): всё только через передачи.
- Новый материал/заказчик/модель после «+ Создать» сразу подставляется в поле; Enter по неизвестному имени открывает создание.
- В передаче склада после добавления обуви форма сбрасывается полностью (включая заказчика).
- Убрано предупреждение «По учёту на складе … проверьте остаток» (идёт перепись склада).
- Операции везде показываются числом (ops_short), включая выбор партии возврата.
- Брак в передаче на склад: кнопка «Добавить брак» → окно выбора обуви, что сейчас на производстве, причина обязательна; пара сразу списывается с остатка производства (stock_moves ref_type='docbrak'); удаление строки/передачи возвращает; при отправке повторно не списывается.
- Приёмка обуви у склада: поле «Принято» пустое, без пересчёта каждой строки принять нельзя (JS + сервер).

## 1.08
- Установка обновлений: перезапуск один раз и одним способом (API с таймаутом 4 с, иначе touch WSGI), повторы чаще 30 с игнорируются; POST /update и откат больше не трогают WSGI сами; страница результата опрашивает /version с таймаутом 5 с, один повтор перезапуска на 45 с. Причина «бесконечной загрузки»: двойной перезапуск (touch + API) и запрос, ждавший ответа API и державший перезапуск. __init__: ожидание _applying до 10 с, зависший — 60 с.
- Расхождения: итог по строке — одна из трёх кнопок (Не догрузили / Нашлось / Потеряно), «Разделить по количеству» по ссылке (пары — целые). Любая сторона предлагает; вторая — «Согласен» (закрыть и провести) или «Не согласен» (причина обязательна, свой вариант необязателен) → dispute, сразу директору. Директор: «Принять вариант …» или «Расписать своё решение».
- discr_case: колонки counter, counter_by; returned → dispute (миграция). В proposal снимок строки (_t,_c,_m,_u,_sent,_got,_short) для закрытых.
- «Расхождения» — вкладки: стороны «Ждут вашего ответа / Ждут другой стороны / У директора / Закрытые», директор «У директора / Идёт разбор / Закрытые». Значок — только дела этой роли (директору — споры).

## 1.09 (исправления по аудиту)
- Обновление: архив раскладывается в _next.tmp и только целиком переименовывается в _next (битый архив не оставляет половину); проверка «это архив jail» (app.py или templates/); копии базы/кода — после успешной раскладки (неудачная загрузка не вытесняет копии); откат тоже через _next.tmp; jail.db* никогда не берётся из архива; MAX_CONTENT_LENGTH 50 МБ; ошибки применения при перезапуске пишутся в errors.log.
- Долг/партии: _received_chunks учитывает только ПРИНЯТЫЕ передачи (раньше — и едущие, из-за чего бралась не та партия).
- Заявка производства: delivered = сумма recv принятых строк передач (from_item), а не collected; «Нашлось» в расхождении пересчитывает и может закрыть заявку (_refresh_need).
- Заявку производства, которая уже едет в передаче, удалить нельзя никому (_req_in_transit).
- Приёмка: пары — только целые (_int_pairs) у склада и производства; опечатка = ошибка, а не «принято всё»; поля пар — только цифры (ui.js).
- Переименование материала переименовывает его в stock_moves, mat_moves, request_items (остаток не теряется); дубль названия запрещён.
- Все POST (кроме /update*) идут под BEGIN IMMEDIATE — проверки и запись атомарны, двойные отгрузки/списания в минус исключены. doc_accept меняет статус условием.
- line_del / request_placed_del проверяют принадлежность строки до удаления.
- Числа: MAX_QTY = 1 000 000, nan/inf/огромные — отказ; деньги до 1e10; id из форм ограничены.
- ui.js: Enter в окне подтверждения нажимает кнопку с фокусом (на «Отмена» — отмена); combo: Enter выбирает выделенный/единственный вариант и ставит единицу, «Создать» — только если ничего не подходит; data-req/data-num/data-max — проверка форм в окне без перезагрузки (склад, материалы, списания, справочники).
- Долг: переплата — подтверждение; показывается «Переплата N ₽» без минуса.
- Очистка пустых черновиков при старте — только старше суток.
- Нижние кнопки «назад» убраны, верхняя «← К списку».
